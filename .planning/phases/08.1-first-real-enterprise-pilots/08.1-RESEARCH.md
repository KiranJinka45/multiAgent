# Phase 8.1 Research: First Real Enterprise Pilots

## Objective
Establish the technical parameters and implementation patterns for the first two "Controlled Enterprise" pilots: **Dependency Remediation** and **CVE Reproduction**.

## 1. Technical Infrastructure Analysis

The Nexus ZTAN codebase already contains the necessary primitives for Phase 8.1 pilots:

- **Sandbox Infrastructure (`packages/sandbox`)**:
    - `SandboxManager`: Orchestrates isolated runtimes (gVisor, Firecracker, Docker).
    - `CanonicalReplayLayer`: Calculates replay hashes (MountHash, ExecutionHash) to ensure 100% replayability.
    - `ExecutionFinalityEngine`: Generates immutable finalized envelopes for auditing.
- **Remediation Engine (`packages/core-engine/src/healer`)**:
    - `AutonomousHealer`: Implements a trap-and-correct loop for sandbox execution failures.
- **Orchestration (`packages/core-engine/src/mission-orchestrator.ts`)**:
    - Handles mission lifecycles, ROI tracking, and state persistence.

## 2. Pilot Workflows

### 2.1 Dependency Remediation Pilot (PILOT-01)
- **Workload**: Automated `npm audit fix` or `pnpm update` within an isolated gVisor sandbox.
- **Gating**:
    - **Read-Only Mounts**: Source code is mounted as RO by default.
    - **Write-Back Gate**: Patches generated by `AutonomousHealer` must pass human review before being applied to the host repository.
- **Replayability**: Every remediation attempt generates a `FinalizedEnvelope` containing the exact command and filesystem state hashes.

### 2.2 CVE Reproduction Pilot (PILOT-02)
- **Workload**: Reproducing a known vulnerability (e.g., path traversal or injection) against a target service in a sandbox.
- **Safety Envelope**:
    - **No Outbound Networking**: Enforced via `SandboxNetworkPolicy` (outbound: false).
    - **Resource Quotas**: Strict CPU/Memory limits to prevent local DoS.
- **Gating**:
    - **Human Approval**: The mission only starts after an operator approves the "CVE Reproduction Profile".

## 3. Operational Controls

### 3.1 Rollback and Recovery (PILOT-03)
- **Rollback Pattern**: Since pilots are "Write-Back Gated", the "host" state is never modified until the final human approval. "Rollback" in this context means discarding the sandbox environment and its proposed patches.
- **Recovery Verification**: Before discarding, the system must verify that the `SandboxLifecycleState` reached "FINALIZED" to ensure forensic logs are preserved.

### 3.2 Cost Ceilings (PILOT-04)
- **Implementation**: The `MissionOrchestrator` will integrate with the `billing` package to check credits/budget before each `SandboxManager.provision()` call.
- **Enforcement**: If a mission exceeds the `SandboxResources.timeoutSeconds` or a pre-defined cost ceiling, the `SandboxManager` will forcibly `destroy()` the instance.

## 4. Implementation Patterns

### HITL Gate Pattern
```typescript
interface PilotGate {
  id: string;
  type: 'HUMAN_APPROVAL' | 'POLICY_CHECK';
  decision?: 'APPROVE' | 'REJECT';
  operatorId?: string;
  rationale?: string;
}
```
All pilots will implement a `MissionStep` that requires a `PilotGate` transition before moving from `READY` to `EXECUTING`.

## ## Validation Architecture

To ensure the success of Phase 8.1, the following validation checks must be implemented:

1. **Isolation Check**: Verify that `SandboxNetworkPolicy` correctly blocks forbidden outbound traffic (Dimensions: 4, 7).
2. **Replay Check**: Verify that `mountHash` and `executionHash` are identical across two independent replays of the same mission (Dimension: 2).
3. **Forensic Integrity**: Verify that `FinalizedEnvelope` is generated even if the sandbox command fails with a non-zero exit code (Dimension: 10).
4. **Economic Gating**: Verify that missions fail to start if the associated project has zero remaining credits (Dimension: 9).
